\hypertarget{introduction}{}
\section{Introduction}

LogGOPSim simulates parallel applications from GOAL schedules that are first converted into a binary trace. The original binary format fixes every node record at 39 bytes with a hard-coded set of fields. Producers that need additional information, such as which GPU performs an operation, therefore reuse existing fields: they pack it into the tag or into resource IDs. The file does not record this, so producer and simulator must agree on the convention implicitly, and a mismatch silently produces wrong results.

This project replaces that format with a \textbf{self-describing, extensible} one while keeping GOAL's operations and dependencies unchanged. The file header describes every field: its name, type, width and position. Producers can add named custom fields without changing the format, each simulator checks at load time that the file supplies what it needs, and fields are packed into only as many bits as their values require. Legacy files remain readable.

\hypertarget{background}{}
\section{Background}

\hypertarget{goal-schedules}{}
\subsection{GOAL schedules}

\textbf{GOAL (Group Operation Assembly Language)} describes the computation and communication of a parallel application as a schedule. It is an intermediate format: a simulator never sees the application itself, only a GOAL schedule describing what each process computes and sends. Schedules are rarely written by hand. Separate generator tools produce them, for example:

\begin{itemize}
\item \textbf{Schedgen} (and its Python rewrite Schedgen2), included with LogGOPSim, generates schedules for MPI collective operations and ML-training communication patterns, and converts MPI traces recorded with the liballprof tracing library.
\item \textbf{ATLAHS} generates schedules from profiled AI training runs (NCCL communication) and from HPC application traces.
\end{itemize}

Because every generator emits the same text format, any of them can feed the same simulator. GOAL has three operations:

\begin{itemize}
\item \texttt{send}: send a number of bytes to another rank.
\item \texttt{recv}: receive a number of bytes from another rank.
\item \texttt{calc}: compute locally for a given amount of simulated time.
\end{itemize}

Operations belong to numbered \textbf{ranks}, usually application processes. Within a rank, operations form a dependency graph: \texttt{requires} waits for another operation to finish, \texttt{irequires} waits for it to start. Sends and receives in different ranks are connected by message matching on source and \textbf{tag}, an integer message label chosen by the application:

\begin{lstlisting}
l1: calc 1000
l2: send 1024b to 1 tag 42
l2 requires l1
\end{lstlisting}

\hypertarget{workflow-generation-conversion-and-simulation}{}
\subsection{Workflow: generation, conversion and simulation}

Getting from an application to simulated times takes three steps, each run as a separate program:

\begin{center}
\resizebox{\linewidth}{!}{\input{diagrams/schedule-pipeline.tex}}
\par\nopagebreak\small\itshape Any generator can produce GOAL; conversion runs once per schedule, and the binary is simulated as often as needed.
\end{center}

\begin{enumerate}
\item \textbf{Generation.} A generator produces the GOAL text from a recorded trace or a workload description, as described above. This step is outside LogGOPSim.
\item \textbf{Conversion.} \texttt{txt2bin} parses the text schedule, resolves labels such as \texttt{l1} to node indices, builds each rank's dependency graph and writes it as binary records. This happens once per schedule.
\item \textbf{Simulation.} LogGOPSim memory-maps the binary file and simulates it with a given set of network parameters. It does not parse text: it reads each node's record directly when it needs it. By default, simulation leaves the binary file unchanged so it can be reused.
\end{enumerate}

The split between conversion and simulation pays off because parsing is done once while simulation is typically repeated, for example to sweep network parameters or compare network models. The binary file is the interface between the two steps, which is why its format is the subject of this project: Sections 3.1--3.4 cover the conversion side and Section 3.5 the simulation side.

\hypertarget{simulation}{}
\subsection{Simulation}

LogGOPSim does not run the application. It walks the schedule's dependency graph and computes \textbf{when} each operation would start and finish, advancing a simulated clock. Each rank's operations are nodes in a graph. A solid edge is a local dependency: \texttt{requires} releases the dependent when the operation \textbf{completes}, \texttt{irequires} when it \textbf{starts}. Messages between ranks are not edges in the file; the simulator pairs each send with a matching receive at run time.

Every node carries a \textbf{dependency counter}: the number of its prerequisites that have not yet been satisfied. Nodes with a counter of zero at the start are the \textbf{roots}. In this example, rank 0 branches and joins again, while rank 1 receives a message and sends a reply:

\begin{lstlisting}
num_ranks 2
rank 0 {
  l1: calc 1000
  l2: send 1024b to 1 tag 42
  l3: recv 1024b from 1 tag 43
  l4: calc 100
  l2 requires l1
  l3 requires l1
  l4 requires l2
  l4 requires l3
}
rank 1 {
  l1: recv 1024b from 0 tag 42
  l2: send 1024b to 0 tag 43
  l2 requires l1
}
\end{lstlisting}

On rank 0, finishing \texttt{l1} makes both the send and the receive ready. Rank 1 receives the request before sending its reply. Rank 0's final calculation waits for both its send and its receive to finish:

\begin{center}
\resizebox{0.68\linewidth}{!}{\input{diagrams/local-dependencies.tex}}
\par\nopagebreak\small\itshape Solid arrows: local completion dependencies. Dashed arrows: matching messages between ranks. Roots have a thick border.
\end{center}

The simulator processes events in time order, starting with the root operations:

\begin{center}
\resizebox{0.85\linewidth}{!}{\input{diagrams/simulation-loop.tex}}
\par\nopagebreak\small\itshape Events are processed in simulated time order.
\end{center}

Processing an event updates the simulated time and operation state, including matching sends with receives. Satisfied dependencies reduce the waiting nodes' counters; reaching zero makes a node ready to run. The result is a predicted finish time for each rank.

This determines what a binary trace must provide for every node:

\begin{itemize}
\item \textbf{Operation fields} used when the node is processed: type, peer, size, tag, CPU and NIC.
\item \textbf{Graph fields} used to release dependents: the dependency counter and the lists of nodes released when a node starts and when it finishes.
\item \textbf{The roots} of each rank, which seed the event queue.
\end{itemize}

Two properties matter for the format. First, a node is needed only when its counter reaches zero, so nodes can be read on demand instead of all at once. Second, the dependency counters are the only values that change during the run; everything else in a node record is read-only.

\hypertarget{required-fields}{}
\subsection{Standard and custom fields}

Not every simulator needs every standard field, so we considered keeping only what is needed to traverse the graph (dependency counts, dependency lists and roots) and making all other fields custom. We kept \texttt{type}, \texttt{peer}, \texttt{size} and \texttt{tag} as standard fields because they are part of GOAL itself: every operation is a send, receive or calculation with a peer, size and tag, so every GOAL simulator needs them. \texttt{cpu} and \texttt{nic} are also part of GOAL, where an operation may omit them and they default to zero, so they stay standard fields as well. They describe LogGOPSim's resource model; ATLAHS, for example, selects GPUs and streams through custom fields instead and simply does not read them. A file may contain fields that a given simulator does not need, since each simulator reads only the fields it binds, and a field with the same value on every node takes no bits per node. Custom fields are therefore reserved for information that GOAL does not define.

\hypertarget{custom-fields}{}
\subsection{Custom fields}

Custom fields are declared in \texttt{config/\allowbreak{}custom\_\allowbreak{}fields.\allowbreak{}toml}, or a TOML file selected with \texttt{txt2bin -\allowbreak{}-\allowbreak{}custom-\allowbreak{}fields <file\allowbreak{}>}, each with a name and an integer type:

\begin{lstlisting}
[[fields]]
name = "gpu_id"
type = "unsigned"

[[fields]]
name = "priority"
type = "signed"
\end{lstlisting}

Producers append \texttt{name value} pairs to every operation, in any order:

\begin{lstlisting}
l1: send 1024b to 1 tag 42 gpu_id 3 priority -2
l2: recv 1024b from 1 tag 42 priority 0 gpu_id 3
l3: calc 1000 gpu_id 3 priority 0
\end{lstlisting}

Invalid or duplicate declarations are rejected, and every declared field must appear exactly once on every operation; missing or invalid values are rejected during conversion. From then on, custom fields are treated exactly like standard fields: their ranges are collected, their widths inferred and their values packed into the same record. Legacy output cannot store them.

Custom fields currently support signed and unsigned integers. Types are defined in one module shared by parsing, statistics and the layout builder, so adding a type means extending that module, the encoding and the parser; float and string types are not implemented.

\hypertarget{inferring-the-layout}{}
\subsection{Inferring the layout}

A compact layout must be chosen before the first record is written: if tags \texttt{0.\allowbreak{}.\allowbreak{}7} fit in three bits but a later rank uses tag \texttt{1000}, records already written cannot be widened. The converter therefore reads the input twice:

\begin{center}
\resizebox{\linewidth}{!}{\input{diagrams/conversion-overview.tex}}
\par\nopagebreak\small\itshape Infer the layout first, then use it to pack every rank.
\end{center}

The first pass keeps only file-wide statistics: each field's minimum and maximum, whether wildcards occur, dependency counts and the largest rank's node count. The second pass parses each rank again and writes its packed records, dependencies and roots using the final layout.

GOAL input is grouped by rank. Each pass builds one rank's graph, collects its statistics or writes its binary data, then frees the graph's memory before parsing the next rank. Graphs for all ranks therefore do not need to fit in memory together, and no temporary file is needed.

This keeps graph memory bounded by the largest rank, but repeats parsing and graph construction. A single rank with a large value range also determines that field's width for the whole file. The alternatives below include ways to avoid the second parse and a way to reduce the work done in each pass.

The temporary-file experiment was removed. On a synthetic 2.1-million-node trace it reduced conversion time from 2.32 s to 1.71 s (1.36\(\times\)), using 193 MB of temporary data. This used a warm file cache without measuring peak memory; it is not reproducible with the current code and does not establish a general speedup.

Alexander Falter is currently implementing a lighter first pass on the GPU. Keeping all graphs is infeasible for large schedules, but the options need not exclude each other: the converter could choose by input size, keeping all graphs in memory when the schedule is small enough and otherwise falling back to a temporary file or two passes.

\hypertarget{field-encoding}{}
\subsubsection{Field encoding}

\textbf{Choosing an encoding.} Sizing each field to its largest value already avoids the legacy format's fixed widths, but a field still costs the bits of its largest value, however little it varies. An encoding stores something smaller than the value itself. If a field is 1024 on every node, the plain value needs 11 bits per node; with offset encoding, 1024 is stored once in the header and each node needs 0 bits. If a field alternates between 1 and 1,000,000, the plain value needs 20 bits, and offset encoding does not help, because offsets still reach 999,999; with dictionary encoding, the header stores the list [1, 1000000] once and each node stores only its index, 1 bit. Offset encoding therefore suits values that lie close together, and dictionary encoding few values far apart. On a Schedgen binomial-tree reduction over 262,144 ranks, offset encoding alone shrinks the record from 39 to 5 bytes (Section 5.2). Combining both, by choosing the cheaper encoding for each field, would probably work best.

Each field is stored as an offset from the smallest observed value. A field with minimum \texttt{m} and maximum \texttt{M} uses \texttt{bit\_\allowbreak{}length(M \(-\) m\allowbreak{})} bits, and the header stores the base \texttt{m}; a constant field therefore uses no bits at all. The reader reconstructs each value as base plus offset:

\begin{center}
\resizebox{0.8\linewidth}{!}{\input{diagrams/offset-encoding.tex}}
\par\nopagebreak\small\itshape Offset encoding: the header stores the base once; each record stores only the offset.
\end{center}

The same rule applies to the graph fields. The dependency counter's range must start at zero, because counters are decremented to zero during simulation. Dependency and root indices refer to nodes within a rank, so their width follows from the largest rank's node count. The four dependency-list fields occupy 16 of the 39 legacy bytes, so packing them matters as much as packing the operation fields.

\texttt{txt2bin -\allowbreak{}-\allowbreak{}report-\allowbreak{}schema} prints the inferred layout, including every field's range, base, width and position.

\textbf{Dictionary encoding (proposed).} Offset encoding can waste bits when a field has only a few distinct values spread over a wide range. For example, \texttt{\{1, 1000000\}} requires 20 bits with offsets. Instead, the converter could use a hash map to assign each distinct value a compact code: \texttt{1 \(\rightarrow\) 0} and \texttt{1000000 \(\rightarrow\) 1}. Each record would then need only one bit for this field. The header would store the reverse dictionary \texttt{[1, 1000000]}, allowing the reader to recover the original value by indexing it with the stored code:

\begin{center}
\resizebox{0.8\linewidth}{!}{\input{diagrams/dictionary-encoding.tex}}
\par\nopagebreak\small\itshape Dictionary encoding (proposed): the header stores the distinct values; each record stores only an index.
\end{center}

 The codes are unique identifiers, not hash values, so hash collisions do not lose information.

This helps when a small set of values occurs repeatedly. The cost is keeping the distinct values during analysis, storing their dictionary in the header, and performing a lookup during encoding and decoding. If most values are distinct, this overhead can outweigh the savings; the converter could compare the total size with offset encoding before choosing. Supporting this requires an encoding-kind marker and dictionary support in the writer and reader. Mutable dependency counters would need special handling because decrementing a code does not decrement its original value.

The first conversion pass already collects each field's range; it would also count distinct values up to a limit. For each field, the converter compares the record bits times the node count plus the dictionary's size in the header, and records the chosen encoding in the field descriptor. Dependency counters always use offsets. Each field then costs at most what either encoding alone would, which matters most for fields such as message sizes, whose few distinct values are often far apart.

\hypertarget{the-file-format}{}
\subsection{The file format}

The new format keeps the same basic components: a rank table, node records, dependency lists and root indices. These still serve the same purposes as in the legacy format; the records and indices now use inferred bit widths instead of fixed widths, changing their storage sizes. The main addition is the schema in the header, which describes this encoding. The existing components are shown in grey:

\begin{center}
\resizebox{\linewidth}{!}{\input{diagrams/file-sections.tex}}
\par\nopagebreak\small\itshape Blue: the schema added to the header. Grey: existing components, with records and indices stored at inferred widths.
\end{center}

The rank counts move into the rank table, and root indices follow the dependency appendix. Records and indices use inferred bit widths. The schema header makes these encodings discoverable by the reader:

\begin{center}
\resizebox{\linewidth}{!}{\input{diagrams/header-details.tex}}
\par\nopagebreak\small\itshape Header and rank table in file order, with one field descriptor and one rank-table entry enlarged; the values are an example and cell widths are illustrative. The fixed prefix holds the magic number, version, header and record sizes, field and rank counts, index width and table offset.
\end{center}

All node records in a file share one layout, so node \texttt{i} of a rank is found directly at \texttt{rank\_\allowbreak{}start + i \(\times\) \allowbreak{}record\_\allowbreak{}size}, without scanning. Dependency and root entries are packed node indices using the file-wide index width. Multi-byte integers are little-endian and bits are numbered from the least significant bit of the first byte, so files are portable between machines.

The magic number distinguishes the new format from legacy files, which keep their own magic and remain readable (Section 3.5.2). Readers reject unknown versions, unknown type codes, truncated headers, overlapping fields and table entries pointing outside the file.

Legacy output remains the default for existing workflows. \texttt{txt2bin -\allowbreak{}-\allowbreak{}format self-\allowbreak{}describing} selects the new format, which also supports custom fields; legacy output warns that it omits them.

\hypertarget{reading-through-simulator-adapters}{}
\subsection{Reading through simulator adapters}

Reading is configured for the simulator that will consume the nodes. The binary may contain more fields than that simulator needs: its adapter selects the fields to decode and specifies where each value goes in the simulator's node struct. Shared graph fields, such as the dependency counter, are filled automatically; other unbound fields are skipped. The same binary can therefore be read into different node types without converting it again.

\hypertarget{connection-and-node-reads}{}
\subsubsection{Connection and node reads}

Each simulator creates its own adapter object. The adapter provides the connection between the stored records and the simulator's input interface:

\begin{center}
\resizebox{\linewidth}{!}{\input{diagrams/schema-agreement.tex}}
\par\nopagebreak\small\itshape Both adapters inherit the same interface, specialized for their node type. Each simulator owns a separate adapter and reader instance.
\end{center}

The node type tells the adapter what to return; it is not a buffer containing every node. Both adapters use the same reader implementation. For file input, each adapter owns its reader and mapping, keeping the bytes alive until the reader is destroyed. The simulators are independent programs and can read a compatible binary concurrently using separate private mappings. Both must support its operations and message-matching convention; the explicit ATLAHS convention in Section 4 currently requires its backend.

All graph simulators' node types inherit a common base that the reader fills automatically: the node's index, its remaining dependency count, and the nodes it releases when it starts and when it completes. The adapter adds only the members its model uses, so supporting a new simulator means declaring its node type and bindings and making its input loader call the reader.

LogGOPSim itself was restructured into the first adapter. Its simulator code moved into its own directory; at startup its adapter opens the file, and the shared reader selects the legacy or self-describing implementation. Event timing, message matching and dependency processing are shared by both formats, so only storage access differs. Along the way, legacy reads were made safe for unaligned data, and empty schedules are now supported.

The procedure has four steps:

\begin{enumerate}
\item \textbf{Define the connection.} The adapter names its node type and binds file fields to that type's members. The member's C++ type tells the reader which values it can accept.
\item \textbf{Prepare once.} The simulator supplies the filename to its adapter, which opens and owns the mapping and constructs the reader. The shared reader checks the schema against the bindings and resolves the selected fields' positions and encodings. Missing fields, incompatible types, values outside the destination type's range and unsupported wildcard representations are rejected before simulation starts.
\item \textbf{Request a node.} The scheduler calls \texttt{adapter.\allowbreak{}read\_\allowbreak{}root\_\allowbreak{}nodes(rank)} to get initially ready nodes, or \texttt{adapter.\allowbreak{}read\_\allowbreak{}node(rank, i\allowbreak{}ndex)} to get a particular node. The reader locates that record and decodes the bound fields directly into the chosen node type. For ATLAHS the result is an \texttt{AtlahsNode}; for LogGOPSim it is a \texttt{LogGOPSimNod\allowbreak{}e}.
\item \textbf{Simulate and continue.} The simulator processes the returned node using its own timing and communication model. As prerequisites are satisfied, it updates dependency counters through the adapter and requests newly ready nodes. The scheduler decides which node to request; there is no sequential \texttt{get\_\allowbreak{}next\_\allowbreak{}node()} operation.
\end{enumerate}

\par\nopagebreak\small\itshape Construct once, then read nodes on demand.
\end{center}

\hypertarget{backward-compatibility}{}
\subsubsection{Backward compatibility}

Existing legacy traces must keep working without conversion, and the simulators should not need a second code path for them. The adapters therefore do not read files themselves: they hold a \texttt{TraceReader}, which looks at the file's magic number and creates one of two readers. Both accept the adapter's field bindings and fill the same node struct.

\begin{center}
\resizebox{\linewidth}{!}{\input{diagrams/backward-compat.tex}}
\par\nopagebreak\small\itshape The format is detected once; the adapter's bindings and node type are the same for both.
\end{center}

\begin{itemize}
\item \textbf{Self-describing files} are read through the header and a decode plan (Section 3.6); any standard or custom field can be bound.
\item \textbf{Legacy files} are read by a small reader that knows the fixed position and width of each standard field in the 39-byte record: type, peer, size, tag, CPU and NIC, plus the dependency count and lists. Each binding becomes a copy from that position into the bound member, so one field may be bound to several members. The member must hold every value of the stored width. Peer and tag store ``any'' as all ones, which becomes the binding's wildcard value. A binding to a custom field is rejected, because the legacy record cannot contain one.
\end{itemize}

An adapter can ask \texttt{is\_\allowbreak{}legacy()} to bind only the fields that exist. LogGOPSim binds the same six standard fields for both formats. ATLAHS binds its eight custom fields only for self-describing files. For legacy files it keeps the upstream convention: the NIC field is bound to both \texttt{Gpu} and \texttt{PeerGpu}, the CPU field to \texttt{Stream}, and messages are matched by tag (Section 4). Neither simulator's scheduler contains format-specific code.

The legacy reader validates each rank's bounds, its roots and its dependency indices when the file is opened, as the self-describing reader does. Files invalidated by an earlier \texttt{-\allowbreak{}-\allowbreak{}save-\allowbreak{}mem} run are rejected with a clear error. The converter still writes the legacy format by default. On the benchmark traces, LogGOPSim's output is identical to that of the original LogGOPSim for both formats (Section 5.3.2).

\hypertarget{validation-before-and-during-simulation}{}
\subsubsection{Validation before and during simulation}

The schema check compares the destination member's type with the \textbf{decoded value range}. The stored bits represent an offset, and decoding reconstructs the original value as \texttt{base + offse\allowbreak{}t}. For example, a 2-bit field stores offsets \texttt{0.\allowbreak{}.\allowbreak{}3}; with a base of \texttt{1000}, it represents values \texttt{1000.\allowbreak{}.\allowbreak{}1003}. Copying such a value into an 8-bit unsigned member would silently truncate it, for example 1002 to 234. The stored code fits in two bits, so a check on the stored width would accept this binding; the reader therefore checks the decoded range, base plus maximum offset, against the member type and rejects the file before any node is read.

Validation is divided between setup and individual reads:

\begin{itemize}
\item \textbf{At setup:} check the schema and bindings, file sections and root lists. Roots must be ordered, distinct, within their rank and initially have a zero dependency counter.
\item \textbf{When reading a node:} check record bounds, dependency indices, operation codes, peer ranks and invalid send wildcards. A simulator can add checks for its own model; ATLAHS, for example, rejects messages larger than htsim supports.
\end{itemize}

\hypertarget{accessing-mapped-data}{}
\subsubsection{Accessing mapped data}

The reader accesses the binary through a memory mapping. The scheduler starts from each rank's roots and requests dependent nodes as their counters reach zero, so the reader decodes nodes on demand.

Dependency lists remain views into the mapped bytes rather than being copied into a new vector for every node. Graph setup validates the immutable dependency indices once; each node read still checks its list bounds, without scanning the indices again. Field-only consumers do not scan dependency arrays. The mapping must stay alive while the lists are used. A consumer that needs a list after closing the mapping must copy its indices first. Analysis tools can bind selected fields into a small struct without inheriting the graph-node base.

\hypertarget{dependency-counters-and-file-reuse}{}
\subsubsection{Dependency counters and file reuse}

Dependency counters change during simulation; the other stored node values stay unchanged. The reader currently decrements counters in the mapped bytes. With the default private mapping (\texttt{MAP\_\allowbreak{}PRIVATE}), the operating system gives a process its own copy of a page when it modifies it. The original file stays unchanged, and each simulation uses a fresh mapping, allowing independent runs to reuse the same binary, including concurrently.

LogGOPSim's \texttt{-\allowbreak{}-\allowbreak{}save-\allowbreak{}mem} instead uses a shared mapping: counter changes reach the file on disk, which is marked unusable for later runs. This mode is destructive and must not be used on an input shared by several simulations. ATLAHS accepts it only for legacy traces, as upstream did; for the new format it always uses a private mapping, because packed counters share bytes with other fields.

Private mappings copy whole pages even when only a counter changes. Keeping the trace read-only and storing counters separately for each run is a possible improvement; its memory and access costs still need measurement.


\hypertarget{runtime-specialization}{}
\subsection{Runtime specialization}

Runtime specialization replaces the shared reader's generic field-decoding loop with code prepared for the opened file and the simulator's bindings. The adapter still exposes the same node-reading interface, and the simulator requests nodes in the same way.

\hypertarget{where-it-fits}{}
\subsubsection{Where it fits}

The file schema and adapter bindings are already resolved at setup. Together, they determine which bits to read, how to reconstruct each value and which node member receives it. The reader turns this information into a specialized decoder once, then uses it for every node read:

\begin{center}
\begin{minipage}{\linewidth}
\centering
\resizebox{0.94\linewidth}{!}{\input{diagrams/plan-runners.tex}}
\par\small\itshape All runners share boundary handling; compiled runners execute C- or LLVM-generated code.
\end{minipage}
\end{center}

The decoders are alternatives behind the same reader interface. Record bounds checks, dependency views and counter updates stay in shared code. Each simulator uses a decoder prepared for its own bindings, even when both read the same binary.

\hypertarget{why-it-could-be-faster}{}
\subsubsection{Why it could be faster}

The generic decoder visits the selected fields for every node, reading their positions, widths and bases from prepared metadata, passing values through \texttt{std::\allowbreak{}variant} and invoking an assignment function per field. A specialized decoder puts these choices directly into its instructions. For a field stored at bit position 13 with width 2 and base 0, for example, it extracts those known bits and stores the result directly into \texttt{node.\allowbreak{}Gpu}.

Knowing these constants lets the compiler simplify shifts and masks, remove the per-field loop and indirect assignments, and combine nearby loads. Field selection already avoids decoding unwanted values; specialization reduces the cost of decoding the selected ones. It does not speed up message matching or network simulation.

\subsubsection{Choosing an approach}

We implemented all four approaches, the in-process JIT with LLVM ORC. All are built from the same \emph{decode plan}, so the interpreter also serves as the fallback when compilation is unavailable.

\hypertarget{decode-plan-and-generated-decoder}{}
\subsubsection{Decode plan and plan runners}

When the reader is constructed, it builds a decode plan with one step per selected field: where the field's bits are (first byte, shift, mask, base, maximum offset) and where its value goes (output struct, member offset and size, value for ANY). The plan is only data. The \texttt{Decoder} resolves and validates the requested fields, builds the plan and selects a runner. The shared \texttt{PlanRunner::decode} uses that runner's fast \texttt{run} when its wide loads are safe, or bounded reads near the end of the mapping. Invalid records are rejected directly. The environment variable \texttt{LOGGOPSIM\_\allowbreak{}DECODER} selects the runner; the shared interface and implementations are shown above.

The runners are:

\begin{itemize}
\item \textbf{\texttt{plan}} (default, \texttt{InterpretedRunner}): runs the steps in a loop, without \texttt{std::\allowbreak{}variant} or \texttt{std::\allowbreak{}function}.
\item \textbf{\texttt{jit}} (\texttt{CompiledRunner} with the system C compiler): turns the steps into a C function, compiles it with \texttt{cc -\allowbreak{}O2 -\allowbreak{}shared -\allowbreak{}fPIC} and loads it with \texttt{dlopen}.
\item \textbf{\texttt{orc}} (\texttt{CompiledRunner} with LLVM ORC): builds the same function as LLVM IR and compiles it in-process, without a compiler process, file or cache. The LLVM code is a plugin, opened only when \texttt{orc} is selected, so other runs do not load LLVM: linking LLVM into the simulator directly added 7--11\,ms to every run. Builds without LLVM fall back to the interpreter. Within one process, readers of the same plan reuse the compiled function. It decodes as fast as \texttt{jit} (about 66\,ns per node in \texttt{decode\_\allowbreak{}bench} on a 524,286-node trace) and spends about 3\,ms more on setup than a cached \texttt{jit}, because it compiles on every run.
\item \textbf{\texttt{templated\_node}} (\texttt{TemplatedNodeRunner}): a template instantiated for each simulator's node type, which fixes the number of steps and each member's size and output struct. The steps are unrolled and every store has a fixed size; bit positions, ranges and member offsets still come from the plan, so one instantiation serves every trace a simulator reads. It needs no compiler at run time.
\item \textbf{\texttt{templated\_schema}} (\texttt{TemplatedSchemaRunner}): a template that takes every step as a template argument, so all positions, masks and ranges are constants, as in the generated C. It only matches traces with exactly the layout it was instantiated for; selecting it on another trace reports the missing match once and falls back to the interpreted runner.
\end{itemize}

\textbf{Runner registry.} The runners are listed in one place, \texttt{RunnerRegistry.\allowbreak{}cpp}. Each entry gives the runner's name, a description, whether it handles any plan, whether it is available in this build (for example, whether a C compiler or the LLVM plugin is present) and a function that creates it for a plan. \texttt{plan} is the default and the fallback. The decoder looks up \texttt{LOGGOPSIM\_\allowbreak{}DECODER} in the registry and rejects unknown names with the list of valid ones; if the runner cannot handle the trace, it says so once and uses \texttt{plan}. The unit tests and the benchmarks take their runners from the same list, so a new runner is tested and measured without further changes. Each runner lives in its own folder with its own build file; adding one means adding the folder, one \texttt{add\_\allowbreak{}subdirectory} line and its registry entry, and removing one is the reverse.

All five runners give identical simulation results. Replaying the 524,286-node trace (\texttt{decode\_\allowbreak{}bench}, 7 interleaved rounds of 20 repetitions, median per repetition):

\begin{center}
\begin{tabular}{lrr}
\toprule
\textbf{Runner} & \textbf{ns/node} & \textbf{Setup (ms)} \\
\midrule
\texttt{plan} & 96.7 & 18.4 \\
\texttt{templated\_node} & 84.3 & 16.1 \\
\texttt{jit} (cached) & 66.5 & 13.1 \\
\texttt{orc} & 66.5 & 15.9 \\
\texttt{templated\_schema} & 66.2 & 12.9 \\
\bottomrule
\end{tabular}
\end{center}

\texttt{templated\_schema} is as fast as the compiled runners: with all constants known, the compiler produces the same code. It is the fastest option without a run-time compiler, but only for traces whose layout was compiled in, and layouts change with each trace's value ranges. We therefore use it as a reference, showing what compiled code costs without compilation, rather than as a runner to choose for new traces. \texttt{templated\_node} helps every trace of a known node type and is 13\% faster than \texttt{plan}; it stays slower than the compiled runners because each step still loads its shift, mask and range from memory.

The generated function contains every offset, shift, mask and range as a constant, with no loop or dispatch; a constant (0-bit) field becomes a single store. An abridged excerpt for a broadcast trace:

\begin{lstlisting}
int decode(const u8* r, u8* const* t) {
  u64 w, c;
  memcpy(&w, r + 0x0, 8);          // type: 2 bits at bit 1, base 1
  c = (w >> 0x1) & 0x3;
  if (c > 0x2) return 0;
  c += 0x1;
  store8(t[0] + 0x38, c);
  memcpy(&w, r + 0x0, 8);          // peer: 16 bits at bit 3
  c = (w >> 0x3) & 0xffff;
  store32(t[0] + 0x3c, c);
  store64(t[0] + 0x40, 0x400);     // size: 0 bits, constant 1024
  /* ... further fields ... */
  return 1;
}
\end{lstlisting}

The source contains only numbers taken from the header, never strings from the trace, so a trace cannot inject code.

\textbf{Fallbacks.} If a fast path rejects a record (a value outside its range, a send to ANY, or a record too close to the end of the file for a 64-bit load), the base class decodes it again exactly and reports the error, so error messages are unchanged. If compilation or loading fails, the reader uses the interpreted decoder. The dependency counter has a matching fast path for decrements.

\textbf{Cache.} Compiled libraries are cached under \texttt{\textasciitilde{}/.\allowbreak{}cache/\allowbreak{}loggopsim-\allowbreak{}jit} (configurable with \texttt{LOGGOPSIM\_\allowbreak{}JIT\_\allowbreak{}CACHE}), keyed by a hash of the generated source, compiler and flags. The source encodes the layout, bindings and destination offsets, so the key covers them. Concurrent builds write under a temporary name and rename. The key does not include the compiler version or target architecture; on a home directory shared between different machines, loading fails and the reader falls back to the plan.

Section 5.3 evaluates the runners against the original decoder, and Section 5.4 compares them across scenarios.

\hypertarget{case-study-explicit-atlahs-metadata}{}
\section{Case study: explicit ATLAHS metadata}

ATLAHS provides workload generators for AI and HPC applications and the htsim packet simulator. We use it as a second consumer of the new format.

\hypertarget{original-encoding-in-standard-fields}{}
\subsection{Original encoding in standard fields}

The legacy record has no GPU field. ATLAHS's NCCL generator models several GPUs per host, so it reuses three existing fields (red):

\begin{center}
\resizebox{\linewidth}{!}{\input{diagrams/legacy-gpu-record.tex}}
\par\nopagebreak\small\itshape How ATLAHS fills the legacy record; nothing in the file records this.
\end{center}

The file cannot say what these values mean: a \texttt{nic} value might be a NIC or a GPU, and the tag's components exist only in the generator's code. htsim therefore guesses the convention from the largest CPU and NIC IDs in the header. A trace that does not fit the guess is simulated with the wrong GPU mapping and no error, and a trace without GPU information cannot be rejected.

\hypertarget{explicit-gpu-stream-and-message-fields}{}
\subsection{Explicit GPU, stream and message fields}

The generator now emits local and peer GPU IDs, the stream and all five message-identity components as separate attributes. The standard CPU, NIC and tag remain zero:

\begin{lstlisting}
before: l2: send 1024b to 1 tag 3050012001 cpu 0 nic 2
after:  l2: send 1024b to 1 tag 0 cpu 0 nic 0 stream_id 0 gpu_id 2 peer_gpu_id 2 chunk_id 3 channel_id 5 sequence_id 12 message_kind 0 communicator_id 1
\end{lstlisting}

The eight attributes need no change to the file format, converter or shared reader. They follow the same custom-field path:

\textbf{1. Declare.} The TOML file declares all eight attributes as unsigned integers:

\begin{lstlisting}
[[fields]]
name = "gpu_id"
type = "unsigned"

[[fields]]
name = "communicator_id"
type = "unsigned"

[[fields]]
name = "channel_id"
type = "unsigned"

[[fields]]
name = "sequence_id"
type = "unsigned"

[[fields]]
name = "message_kind"
type = "unsigned"

[[fields]]
name = "chunk_id"
type = "unsigned"

[[fields]]
name = "stream_id"
type = "unsigned"

[[fields]]
name = "peer_gpu_id"
type = "unsigned"
\end{lstlisting}

\textbf{2. Convert.} \texttt{txt2bin} collects each field's range and chooses its width, as for standard fields.

\textbf{3. Describe.} The header stores each field's name, type, base, width and position.

For the four-GPU example trace, conversion produces this packed record layout:

\par\nopagebreak\small\itshape Four-GPU example: 2 bytes per node instead of 39, including all eight custom fields.
\end{center}

\textbf{4. Bind.} The ATLAHS adapter supplies this node type. It inherits the common graph fields and adds the operation fields and explicit metadata its scheduler needs:

\begin{lstlisting}
struct AtlahsNode : BaseDeserializedGraphNode {
    std::uint8_t Type = 0;
    std::uint32_t Peer = 0;
    std::uint64_t Size = 0;
    std::uint32_t Tag = 0;
    std::uint8_t Proc = 0;
    std::uint8_t Nic = 0;
    std::uint32_t Gpu = 0;
    std::uint32_t PeerGpu = 0;
    std::uint32_t Stream = 0;
    std::uint64_t Communicator = 0;
    std::uint64_t Channel = 0;

};
\end{lstlisting}

For example, this binding maps the declared \texttt{gpu\_\allowbreak{}id} field to \texttt{Gpu} in the returned node:

\begin{lstlisting}
bind_field(std::string{"gpu_id"}, &AtlahsNode::Gpu)
\end{lstlisting}

The other seven attributes bind to \texttt{PeerGpu}, \texttt{Stream}, \texttt{Communicator\allowbreak{}}, \texttt{Channel}, \texttt{Sequence}, \texttt{MessageKind} and \texttt{Chunk} in the same way. Missing or incompatible fields are rejected at setup. \texttt{start\_\allowbreak{}time} is runtime state maintained by the scheduler, rather than a stored field.

\textbf{5. Use.} \texttt{Gpu} selects the local GPU and \texttt{PeerGpu} the remote GPU; on a send these are the source and destination, respectively. \texttt{Stream} selects the execution stream. Receive matching compares the source and the \texttt{(Communicato\allowbreak{}r, Channel, \allowbreak{}Sequence, Me\allowbreak{}ssageKind, C\allowbreak{}hunk)} tuple, and checks that both GPU endpoints agree with the receive.

With the new format htsim no longer guesses: the GPU count is the field's maximum plus one, read from the header. Legacy ATLAHS traces still work: for them the adapter binds the NIC to \texttt{Gpu} and \texttt{PeerGpu} and keeps the upstream mapping.

\hypertarget{integration}{}
\subsection{Integration}

Declaring and binding the eight fields makes them available to ATLAHS, but its existing code also has to produce and use them. We changed three points along the path from workload generation to simulation.

\hypertarget{generator-emit-the-original-values}{}
\subsubsection{Generator: emit the original values}

Previously, the NCCL generator encoded the GPU in the NIC field and combined message-identity components into a decimal tag. We added a new option, \texttt{-\allowbreak{}-\allowbreak{}explicit-\allowbreak{}fields}, to the generator. With it, every operation carries eight additional named attributes instead of packed numbers: the GPU it runs on, the GPU of its communication partner, its execution stream, and the five components of its message identity. To find the partner's GPU, the generator looks up which GPU the peer rank uses in that communicator and converts it to a dense host-local index (0, 1, 2, \ldots); this works for point-to-point, ring and tree communication. This preserves their values before they enter the converter, avoiding the ambiguity of reconstructing them from overloaded fields. Calculations and fences supply zero-valued identity attributes because they do not participate in message matching. Generation without the option keeps the original output convention.

\hypertarget{input-loader-construct-the-schedulers-nodes}{}
\subsubsection{Input loader: construct the scheduler's nodes}

The existing ATLAHS loader read legacy records using fixed byte offsets. It now constructs an \texttt{AtlahsAdapte\allowbreak{}r} that owns the mapping and reads either format. When the scheduler needs a node, the loader obtains an \texttt{AtlahsNode} through that adapter. The shared reader handles field positions and decoding, while the adapter supplies the bindings and ATLAHS-specific checks. The rank scheduler reads only the dependency list released by each event. A single release helper updates counters and carries the latest prerequisite completion time into newly ready nodes. The old converter's graph writer is kept separately from this runtime loader.

This is where the generic format connects to the existing simulator: the scheduler receives the operation fields it already uses, together with explicit GPU, stream and message identity. Legacy files use the same adapter, which binds only the standard fields and binds the NIC to both GPU members to preserve their GPU mapping (Section 3.5.2).

\hypertarget{scheduler-use-the-explicit-metadata}{}
\subsubsection{Scheduler: use the explicit metadata}

Upstream used the sender's GPU index at both network endpoints: a send from A/GPU 0 to a receive on B/GPU 2 still travelled to B/GPU 0.

\begin{center}
\resizebox{0.44\linewidth}{!}{\input{diagrams/gpu-routing.tex}}
\par\nopagebreak\small\itshape Upstream delivered every message to the sender's GPU index on the receiving host.
\end{center}

 We added \texttt{peer\_\allowbreak{}gpu\_\allowbreak{}id} and changed endpoint selection to use \texttt{Gpu} at the source and \texttt{PeerGpu} at the destination. Queues and completion callbacks retain both endpoints, so matching checks the intended GPU pair and updates each host's own resource clocks. htsim's packet transport model stays the same.

Execution clocks use the explicit 32-bit \texttt{Stream} member rather than the 8-bit CPU field; the stream count comes from the schema. Legacy input retains its original routing; its adapter binds the CPU field to \texttt{Stream}.

Message matching also had to change. Previously, the matcher compared numeric tags containing concatenated components. Minimum-width decimal padding did not impose a maximum component size, so different component tuples could produce the same tag. For example, chunk 1, channel 2, sequence 12345 and chunk 10, channel 21, sequence 2345 (both with kind 0 and communicator 1) both produce the tag \texttt{10212345001}, because the five-digit sequence number shifts the other components:

\begin{center}
\resizebox{0.85\linewidth}{!}{\input{diagrams/tag-collision.tex}}
\par\nopagebreak\small\itshape Two different messages produce the same concatenated tag.
\end{center}

 For explicit-field messages, both the waiting-receive and unexpected-message queues now compare the source and the complete \texttt{(Communicato\allowbreak{}r, Channel, \allowbreak{}Sequence, Me\allowbreak{}ssageKind, C\allowbreak{}hunk)} tuple. The identity travels with the message through the network completion callback, so matching works whether the receive or message arrives first. Components remain unsigned 64-bit values throughout, avoiding narrowing or lossy replacement with a hash. If several queued operations match, the shared matcher selects the lowest operation index, preserving schedule order rather than relying on queue insertion order.

Legacy messages retain numeric-tag matching. Explicit-field messages require \texttt{tag 0}, message kinds keep the generator's values 0--5, and unmatched messages cause the run to fail. These checks prevent the two identity conventions from being mixed silently.

\textbf{Compatibility boundary.} The ordinary LogGOPSim matcher still supports numeric tags only, so its adapter rejects explicit ATLAHS messages. Running this particular trace in LogGOPSim would also require tuple-based matching there; accepting the file schema alone does not supply that behavior.

The modified ATLAHS source is a separate fork of a fixed upstream revision, cloned beside LogGOPSim; only the adapter lives in LogGOPSim. Build instructions are in \href{\detokenize{../src/LogGOPSim/simulators/atlahs/README.md}}{the adapter README}.

Integration results, including the complete recorded-workload comparison, are reported in Section 5.1.

\hypertarget{remaining-conventions}{}
\subsection{Remaining conventions}

Other conventions remain:

\begin{itemize}
\item ATLAHS also includes GOAL-generation paths for MPI/HPC workloads (\texttt{goal\_\allowbreak{}gen/\allowbreak{}hpc}, using PMPI traces and Schedgen) and distributed-storage workloads (\texttt{goal\_\allowbreak{}gen/\allowbreak{}storage}, using DirectDriveSim). We adapted only the NCCL generator. The others can still use the legacy simulation path, but their output cannot directly use our explicit-field ATLAHS adapter: their generators would first need to supply the required attributes with meanings appropriate to those workloads.
\item GPU IDs are consecutive local indices (\texttt{0, 1, 2, \ldots{}}), which the modified NCCL generator assigns automatically from the recorded GPU identifiers. The simulator maps each host/GPU pair to a network endpoint using \texttt{host\_\allowbreak{}rank \(\times\) gpu\_\allowbreak{}count + gpu\_\allowbreak{}id}, where \texttt{gpu\_\allowbreak{}count} is the file-wide maximum local GPU ID plus one. The topology must therefore provide enough endpoints for this mapping: two hosts with four GPUs each require eight endpoints. Our test topologies satisfy this requirement; custom traces and topologies must use the same mapping. Hosts with fewer GPUs still reserve endpoint slots according to the file-wide GPU count.
\end{itemize}

\hypertarget{evaluation}{}
\section{Evaluation}

\hypertarget{correctness}{}
\subsection{Correctness}

The automated tests are split in two. \textbf{Unit tests} (\texttt{tests/\allowbreak{}unit/}, GoogleTest) check individual components in-process. \textbf{Integration tests} (\texttt{tests/\allowbreak{}integration/}, pytest) run the built programs end to end: converter, simulators, ATLAHS generator and the recorded workload. CTest runs both and labels them, so \texttt{ctest -\allowbreak{}L unit} runs only the fast tests; shared inputs are in \texttt{tests/\allowbreak{}data/}. The checks cover:

\begin{itemize}
\item \textbf{Format components:} header and rank-table round trips, byte order, packing at every bit alignment and width, wildcards, signed and custom fields, and rejection of malformed files.
\item \textbf{Conversion:} new files are decoded independently and compared field by field with legacy output, including dependency lists, roots, wildcards, multiple custom fields and 64-bit values.
\item \textbf{Specialized decoders:} a differential test generates 300 random layouts (widths 0--64, gaps, signed bases, wildcards, fields spilling into a ninth byte) with 2,000 random records each; 321,042 of the records are valid and 278,958 invalid. Every runner of the registry that handles any plan must accept exactly the records the exact decoder accepts and produce identical values, and the exact decoding into member destinations must agree as well; counter decrements must leave neighbouring bits unchanged. Removing the spill-byte load or the send-to-ANY check makes the test fail. Every runner, including the templated ones, also reads a trace that ends directly before a protected memory page. On all five benchmark traces, simulation results match the legacy format.
\item \textbf{Simulation:} on a saved reference trace (\texttt{binomialtree\allowbreak{}bcast\_\allowbreak{}8}), the new format must reproduce the original simulator's per-rank finish times. Further tests cover both message arrival orders and both protocols, a regression test for the eager/rendezvous bug described below, and 60 random schedules with wildcards, start dependencies, several CPUs and NICs, mixed message sizes and custom fields, which must simulate identically in both formats under four network parameter sets.
\end{itemize}

Comparing the restructured simulator with the original also exposed an existing bug in LogGOPSim's eager/rendezvous handling. A small message is sent eagerly, without waiting for the receiver, and the sender completes immediately. If the message arrived before a larger receive was posted, which MPI allows, the receive side decided by its own buffer size that the message was rendezvous and completed the sender a second time. The original simulator let the dependency counter underflow silently and reported wrong times; in a two-rank example, a sender that should finish at 1,700 was reported at 100,000. The receive side now decides by the message's size, as the sender did.

Beyond the test suite, a one-off audit compared the new code with the original LogGOPSim on 1,480 schedules: 60 Schedgen collectives and 1,420 random graphs, each simulated with four network parameter sets. The legacy output of the new converter was byte-identical to the original's, and both formats reproduced the original simulator's results in all 5,920 simulations. This excluded the eager/rendezvous bug above. The original simulator crashed on two kinds of input: ranks without operations, which the new simulator handles, and Schedgen schedules that address non-existent ranks, which the new converter rejects with an error. The test suite also passes under AddressSanitizer and UndefinedBehaviorSanitizer, and 2,000 randomly corrupted files were each either rejected with an error message or simulated normally, without a crash.

\hypertarget{reading-dependency-lists-only}{}
\subsubsection{Reading only the required dependency list}

LogGOPSim originally decoded a full node when it became ready, started and finished. Replacing the latter two reads with list-only access helped, but the first version still read both lists for each event. The scheduler now calls \texttt{read\_\allowbreak{}dependents(rank, index, event)}, selecting \texttt{DependencyEvent::Start} or \texttt{DependencyEvent::Finish} before decoding. It reads only the selected list's position and count and builds one view. The legacy path makes the same selection.

The packed reader reuses \texttt{FieldSource}, resolving byte positions, shifts, masks and load extents at setup instead of maintaining separate extraction arithmetic. Zero-bit fields return their constant base without loading record bytes. Node indices and slice positions remain checked, including constant empty lists; wide fields and mapping tails keep their safe read paths. No dependency arrays are copied or allocated per read.

\textbf{Which runner wins where.} No single runner is best everywhere:

\begin{itemize}
\item \textbf{Tiny traces} (bcast\_8): \texttt{plan}; there is nothing to amortize.
\item \textbf{One-shot runs up to a few hundred thousand nodes}: \texttt{templated\_node}.
\item \textbf{One-shot runs on large traces} (dissem\_16k): \texttt{orc}.
\item \textbf{Repeated runs and long simulations}: \texttt{jit} (with a warm cache) or \texttt{orc}, which tie.
\item \texttt{templated\_schema} matches the compiled runners without compiling anything, but only for layouts compiled in; here it covers the benchmark traces themselves. It serves as a reference, not as a choice for new traces.
\end{itemize}

A sensible automatic choice would therefore be \texttt{plan} for tiny traces, \texttt{jit} when its cache already holds the trace's decoder, and otherwise \texttt{templated\_node} or \texttt{orc} by trace size. We have not implemented this yet.

\hypertarget{limitations-and-future-work}{}
\section{Limitations and future work}

\textbf{Cheaper conversion.} Both passes currently run the full parser and build complete graphs. Section 3.3 compares lighter passes with alternatives that avoid the second text parse. Implementing and comparing these designs for conversion time, peak memory and temporary storage remains future work.

\textbf{Better compression.} Dictionary encoding, described in Section 3.3.1, remains a proposed alternative to offsets. Separately, the start-dependency position \texttt{sDepIx} always equals \texttt{depIx + nDep\allowbreak{}} and could be derived instead of stored.

\textbf{Richer metadata.} The header does not yet describe units, which operations a field applies to, default values or provenance. A canonical schema hash would let decoders be cached by layout.

\textbf{Standard field limits.} Standard fields are still limited by the parser and simulator types they are stored in, for example 32-bit tags and 8-bit CPU IDs; widening them requires changing those paths together, not only the file layout.

\textbf{Remaining decoding overhead.} Dependency indices are validated once at graph setup, ready-node buffers are reused, and starting or finishing a node reads only its dependency lists (Section 5.3.2). Excluding the 14-node trace, current replay medians span roughly 13--41\,ns per node against 7--27\,ns for legacy records; profiling points to dependency-list access and record lookup. The unused list reads are now removed. Repeated rank lookup, packed-index iteration and counter updates remain candidates for measurement; sampling alone does not establish memory latency as the cause.

\textbf{Decoder selection.} The interpreted runner is the default and the others are selected with an environment variable; a command-line option would be more convenient, and Section 5.4 suggests choosing the runner automatically. Since a failed compilation or a missing template instantiation falls back to the interpreter, the adapters report which runner is in use (\texttt{get\_\allowbreak{}runner\_\allowbreak{}name}); LogGOPSim prints it, and the simulation tests run with every runner.

\textbf{Evaluation.} The measurements in Sections 5.3--5.5 come from one laptop; Section 5.6 lists what remains.

\textbf{Parallelization.} The simulator and converter are single-threaded. OpenMP parallelization and further optimizations are planned.

\hypertarget{conclusion}{}
\section{Conclusion}

The project replaces LogGOPSim's fixed 39-byte binary trace with a self-describing format whose header names every field and gives its type, width and position. Producers can add custom fields without changing the format, readers validate at load time that a file supplies what each simulator needs, and fields are packed into only as many bits as their values require. The ATLAHS case study makes GPU and message identity explicit, replacing overloaded NICs and concatenated tags with validated fields and tuple-based matching. Correctness is established by the test suite against the original simulator. Runtime specialization recovers most of the decoding overhead: a decoder compiled for the file's schema decodes nodes 4--6\(\times\) faster than the generic decoder, with the current complete-simulation results reported in Section 5.3.1. Five runners share one decode plan behind a registry, and preliminary scenario benchmarks show that the best one depends on trace size and whether a run is one-shot or repeated (Section 5.4). The broader performance evaluation remains to be completed.
